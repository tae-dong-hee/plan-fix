# 계정 복구 요청 제한

`RecoveryRequestLimiter`는 접속한 socket peer를 HMAC 처리해 시간당 요청 수를 제한한다.
이는 개별 사용자의 실제 IP별 제한이 아니다. Cloud Run 또는 프록시 뒤에서는 여러 사용자가
같은 peer를 공유할 수 있으므로, 기본 상한을 넉넉하게 두고 개별 메일·계정 제한을 함께 적용한다.
클라이언트가 임의로 보낸 `X-Forwarded-For`는 신뢰하지 않는다.

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| `RECOVERY_REQUESTS_PER_PEER_HOUR` | 1000 | 아이디·비밀번호 메일 요청이 공유하는 peer별 상한 |
| `RECOVERY_CONFIRMATIONS_PER_PEER_HOUR` | 3000 | 비밀번호 재설정 확인 요청의 peer별 상한 |

아이디 찾기는 정규화한 이메일별 시간당 5회·60초 간격으로 제한한다. 비밀번호 찾기는
아이디별 시간당 20회 제한과 실제 계정의 60초 재발송 제한을 적용한다.
요청 제한 트랜잭션은 계정 작업 트랜잭션보다 먼저 완료하므로 입력 오류·발송 실패 때도
횟수가 보존되며, 외부 트랜잭션이 연결을 점유한 상태에서 추가 DB 연결을 기다리지 않는다.

제한값은 양수만 허용한다. 영속적인 HMAC 버킷을 사용하므로 여러 서버 인스턴스에서도
제한을 공유하고 이메일·아이디·peer 주소의 원문은 quota 테이블에 저장하지 않는다.

## 재시도 시간 안내

계정 복구에서 제한에 걸리면 `429` 응답에 `Retry-After` 초 값을 보낸다. 60초 재발송
간격과 시간당 한도가 동시에 적용되면 두 제한이 모두 끝나는 시각을 사용한다. 남은 시간이
1초 미만이어도 올림하므로 안내한 시각에 재시도했는데 아직 제한 중인 상황을 줄인다.
거절된 요청은 기존 윈도나 마지막 발송 시간을 연장하지 않는다.

아이디·비밀번호 **메일 요청 화면**은 남은 시간을 시·분·초로 표시하고 해당 입력의 재제출을
막는다. 비밀번호 찾기의 아이디, 아이디 찾기의 이메일을 다른 값으로 고치면 이전 입력의
화면 대기는 해제한다. 이메일 대소문자·공백 수정은 같은 주소로 취급한다. 공유 접속 제한이나
원래 계정의 제한은 서버에서 계속 검사하므로 입력 변경으로 발송 한도를 우회할 수 없다.
기존 비밀번호 확인 화면의 429 처리는 이 화면 개선 범위에 포함하지 않는다.

`Retry-After`는 허용된 CORS 출처에서도 읽을 수 있다. 헤더가 없거나 올바른 양의 정수가
아니면 화면은 60초를 사용한다. 입력 불일치(`400`)나 발송 실패(`503`)를 요청 한도로
취급하지 않는다. 메일은 가입 시 등록한 주소로만 발송하며, 수신하고 싶은 다른 주소를
입력하면 계정 불일치로 거절한다.

## 2026-09-19 재시도 안내 검증

- 최신 main `287949c` 위에서 백엔드 94개 스위트·661개 테스트, 프런트엔드 56개 파일·870개 테스트 통과.
- 백엔드 실행 JAR, 프런트엔드 타입 검사와 운영 빌드 성공.
- 60초 쿨다운·시간당 한도 경계, 소수 초 올림, 재시도 시 윈도 연장 방지, 동시 요청의 마지막 허용 1회, 실패 후 한도 보존 검증.
- 일반 오류와 기존 다른 기능의 429 호환, 허용 출처에서의 헤더 노출과 다른 출처 차단 검증.
- 메일 요청 화면의 재제출 차단·만료 후 재시도·다른 계정으로 수정·같은 계정의 표기만 변경하는 경우 검증.
- 398×844 모바일에서 35분 27초 응답을 주입해 남은 시간·버튼 잠금을 확인. 브라우저 실행 오류와 가로 넘침 없음.

운영 원인 확인은 제한 횟수·남은 시간과 입력 계정의 일치 여부만 읽었다. 제한 행이나 계정,
비밀번호는 변경하지 않았고 SMTP 설정·DB 스키마 변경도 없다.
